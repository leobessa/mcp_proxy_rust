When one call fails, should the whole session go down?

A demo of how mcp-proxy reacts when the server refuses a single request. Press the buttons and watch what the editor on the other end actually receives.

The question this answers. Right now the proxy treats any failure to send a request as the whole connection dying: it tears the session down, hides the request in a buffer, reconnects, and replays it. That is the correct thing to do when the server has genuinely gone away. It is the wrong thing to do when just one call failed — the editor sits waiting, and eventually gets an error blaming the transport for what was really one bad call.

So: should the proxy tell those two situations apart? The two columns below run the same events through today's rule and through a proposed rule that answers the failing call directly and leaves the connection alone. Scenario 3 is the one that matters most — it checks the proposed rule doesn't break the case buffering exists for.
